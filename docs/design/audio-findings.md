## Вывод

**Фоновое воспроизведение работает через HTML5 `<audio>` + Media Session API внутри WebView.** Отправка трека файлом в чат как основной механизм не нужна.

Что это значит для проекта:

- Кассета строится по плану, без гибридной схемы.
- `requestBackgroundFallback()` остаётся заглушкой — на случай Android-устройств, где поведение может отличаться.
- Системный плеер полноценный: play, pause, переключение треков и **перемотка**. Значит WebView пробрасывает `seekto` в страницу — но только если обработчик зарегистрирован. Без `setActionHandler('seekto')` ползунок на локскрине не реагирует.
- Отсюда правило для движка: **все шесть обработчиков обязательны** (`play`, `pause`, `previoustrack`, `nexttrack`, `seekto`, `seekbackward`/`seekforward`), а после перемотки сразу обновляется `setPositionState`.
- Метаданные на локскрине (обложка, название, артист) — часть продукта, их надо заполнять всегда, включая обложку 512×512.

## История проверки

Первый прогон спайка дал «перемотка не работает» — но в той версии не было обработчика `seekto`. После его добавления перемотка с локскрина заработала. Вывод: проверять механизм только с полным набором обработчиков, иначе легко списать на ограничение платформы то, что не реализовано.

## Замечание про точность времени

Интерфейс отстаёт на доли секунды. Причина: время берётся из таймера/события `timeupdate`, которое приходит 4 раза в секунду.

Как правильно:
- **источник истины — `audio.currentTime`**, читать его на каждом кадре (`requestAnimationFrame`) во время воспроизведения;
- в стор писать с троттлингом (4 раза в секунду), но отрисовку цифр и прогресса делать по `currentTime`;
- на паузе — просто перерисовать один раз.
