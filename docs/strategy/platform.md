# Стратегия: как это масштабируется

Два вопроса на будущее и технические ответы на них. Записано, чтобы решения не терялись и чтобы сегодняшний код не пришлось выбрасывать.

---

## 1. Перенос Mini App в полноценное приложение

**Короткий ответ: да.** Основа — React + TypeScript, то есть обычный веб. Вопрос не «можно ли», а «сколько стоит и что придётся переписать».

### Три пути

| Путь | Что делаем | Что переиспользуем | Оценка работ | Качество |
|---|---|---|---|---|
| **Capacitor / Tauri** | веб-приложение заворачиваем в нативную оболочку | весь UI, вся логика | 1–2 недели на оболочку + доводка аудио | нормально, но анимации и аудио ведут себя как в вебе |
| **React Native (Expo)** | UI переписываем на RN, логику оставляем | логика, стор, парсеры, типы, API — 40–60% кода | 4–8 недель | хорошо, нативно ощущается |
| **SwiftUI + Kotlin** | UI и плеер пишем заново | только доменная логика и спецификации — 25–35% | 8–16 недель (две платформы) | лучшее, что можно получить |

### Что переносится всегда

- Модель данных (`artist` / `release` / `track`), API, бэкенд.
- Парсер LRC, логика очереди, шаффла, повторов.
- Фан-слой: статистика, проявление обложек, титулы — это чистая логика.
- Дизайн-система как **спецификация**: токены, сетка, типографика. CSS-переменные потом один раз переносятся в тему RN или Swift.
- Контент-пайплайн: обложки, палитры, LRC.

### Что придётся делать заново

- Кассета: 3D-флип, катушки, лента. На Swift/Kotlin это отдельная работа, на RN — частично Core Animation/Reanimated.
- Telegram-обвязка: `initData`, `BackButton`, `HapticFeedback`, Stars. Заменяется на deep links, нативные жесты и **IAP** (Apple/Google забирают 15–30% — экономика подписки меняется).
- Медиа-слой: зато нативное приложение решает главную боль — фон и локскрин работают по-настоящему, без костылей WebView.

### Что сделать уже сейчас, чтобы перенос был дешёвым

1. **Никакого Telegram SDK вне `src/app/telegram.ts`.** Весь UI не знает, что живёт в Телеграме.
2. **Аудио за интерфейсом `AudioPort`** (`play`, `pause`, `seek`, `load`, `subscribe`). Сегодня реализация — `<audio>` + Media Session, завтра — нативный плеер, код UI не меняется.
3. **Слой данных за репозиториями** (`CatalogRepo`, `PlaybackRepo`), без прямых `fetch` в компонентах.
4. **Никаких CSS-хаков, завязанных на WebView.** Только стандартный CSS.
5. **Дизайн-токены одним файлом**, без значений, размазанных по компонентам.

При таком разделении: Capacitor — почти бесплатно, RN — переписать только `src/ui` и `src/features/*/components`, нативка — переписать UI, оставив `src/domain`.

## 2. Из «приложения одного артиста» в полноценный стриминг

**Короткий ответ: да, архитектурно это заложено.** Но главный барьер — не дизайн и не код, а **права на музыку**.

### Что уже artist-agnostic

- Модель данных: `artist`, `release`, `track`, у релиза есть `artistId`. Добавить второго артиста — это данные, а не код.
- Полярность от обложки работает для любой обложки.
- Проявление обложек, статистика, титулы — общие механики.
- Контент-пайплайн (обложка → палитра → LRC) не зависит от артиста.

### Что придётся переделать

| Слой | Сейчас | В стриминге |
|---|---|---|
| Навигация | каталог одного артиста | главная с подборками, поиск по всему, страницы артистов, библиотека |
| Кассета | единственный плеер | скин/плеер по выбору; по умолчанию — нейтральный |
| «Моя волна» | радио одного артиста | рекомендации по всему каталогу (нужен бэкенд и данные) |
| Титул | про одного артиста | титул по всему профилю + топ-артисты |
| Проявление | все релизы одного | только те, что в твоей библиотеке |

### Что станет главным (и дорогим)

1. **Лицензии.** Это 80% работы. Варианты по возрастанию сложности:
   - независимые артисты с прямыми договорами (то, с чего начали с Кишлаком) — дешево, но каталог маленький;
   - дистрибьюторы/агрегаторы как посредники за процент;
   - мейджоры — долго, дорого, только с юрлицом и историей.
2. **Бэкенд и стриминг.** Каталог, авторизация, подписанные ссылки на файлы, CDN, лимиты, аналитика. Из «статика + JSON» превращается в сервис.
3. **Деньги.** В Телеграме — Stars; в нативном приложении — IAP с комиссией 15–30%; плюс выплаты правообладателям и отчётность.
4. **Юридика.** Оферта, DMCA-процедура, налоги, возрастные ограничения.

### Честные сроки (грубо)

- Второй артист в текущей архитектуре — недели, не месяцы: это данные и страница артиста.
- «Стриминг для всех» с легальным каталогом и подпиской — 3–6 месяцев работы команды плюс переговоры по правам, которые могут идти дольше кода.

### Опасные пути (не делать)

- Тянуть чужую музыку из Deezer/YouTube/VK «как конкурент» — это не бизнес-модель, а отсрочка бана. Каталог есть, но платить некому и защищаться нечем.
- Делать вид, что «мы просто плеер», и раздавать чужие треки — первый же правообладатель закрывает бота.

### Что фиксируем сейчас

- Модель данных — только `artistId`-связи, без «единственного артиста» в коде.
- Плеер — интерфейс, кассета — одна из реализаций, не единственная.
- Навигация — без хардкода «один каталог»: роуты вида `artist/:id`, `release/:id`.
- Фан-слой считает статистику по `artistId`, а не глобально — потом пригодится.
